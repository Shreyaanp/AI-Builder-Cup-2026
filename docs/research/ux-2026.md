## 1. Expressiveness should direct attention

**Published guidance.** Google's research explores colour, shape, size, motion and containment as ways to strengthen hierarchy and emotional engagement. Its study results are context-specific; they do not establish Chalkboard's task completion or retention. Material's current public hub also presents expressive typography, shape, components and motion. [Google's expressive-design research](https://design.google/library/expressive-material-design-google-research), [Material 3](https://m3.material.io/).

**Recommendation.** Preserve the chosen Chalkboard identity. Owner: a useful decision, one prominent action, quiet supporting lists. Customer: vivid imagery, one surprising find, then a meaningful stamp or reveal. Both audiences share roles, controls and navigation behavior. Do not put a saturated colour, handwritten heading, animated counter and reward badge on every card. The difference should be emphasis, not two incompatible systems.

**Observed.** `src/design/customerTheme.ts:8` already shares `nivaTheme`; the earlier greyscale diagnosis in visual-motion.md is historical. `src/design/theme.ts:59` resolves `chalkRoles` from `chalkboard.ts`, so generated Material JSON is **not** the current runtime palette authority. Do not regenerate JSON and assume the app changed.

**Concrete hand-off.** Keep literals inside `chalkboard.ts`; components consume `theme.material` and paired `theme.chalk` roles. Retain `surface/onSurface` for reading, `surfaceContainerLow` for quiet groups, `primary/onPrimary` for the decision, `errorContainer/onErrorContainer` for actionable errors. Changes to generated roles must deliberately reconcile with this runtime architecture. Recheck paired roles after hover, disabled, alpha overlays and custom status palettes.

## 2. Motion and shape form a small grammar

**Published guidance.** Material now describes a physics-based spring system with standard and expressive schemes. Spatial movement and effects have different behavior; opacity and colour should not overshoot. Web compatibility does not mean MUI automatically implements Compose motion tokens. [Material motion physics](https://m3.material.io/styles/motion/overview/how-it-works).

**Observed.** `theme.ts:25` exports duration/easing tokens; `chalkMotion.ts:15` gates GSAP with matchMedia and cleanup. That is a usable web adaptation, not proof of a native Material spring implementation.

**Recommendation.** Keep the current implementation vocabulary until a measured task justifies change. Owner: selected supplier → order review; changed price → Updated. Customer: one stamp landing → settled progress. Each contract names **one** motion moment, with an immediately understandable static end state. Never delay Confirm, Done or typing for animation. Avoid infinite decorative movement beside reading; provide pause/stop for persistent non-essential animation. Animate transform/opacity for web mechanics. Review existing clip-path/stroke effects separately for paint cost before extending them.

Use existing `shape` steps by purpose: input small corners; grouped content medium/large; journey container larger; pill only for an appropriate button/chip. Use the die-cut sticker shape for an earned reward, not an everyday input. Shape must reinforce meaning alongside text, not replace labels.

## 3. Conversation is a journey, not an empty textbox

**Published guidance.** Conversation design treats turns and recovery as deliberate interaction design. Google's error guidance distinguishes no-input/no-match/system recovery; it is historical voice-product guidance, not a guarantee of current Gemini behavior. [Conversation design](https://design.google/library/conversation-design-intro), [error handling](https://developers.google.com/assistant/conversation-design/errors).

**Recommendation.** `CoachScreen` and the onboarding worker should establish the next useful response before showing optional examples. Name first, kind second, then only profile-relevant questions. Never invent a name or silently complete an unanswered factual field. Silence may produce a helpful suggestion, but acceptance and public facts still need an owner's explicit answer/review.

In `InputDock` and `useVoice`, distinguish Idle → Requesting permission → Listening → Processing → Speaking → Interrupted/Error. The orb reflects the actual state; captions and the listening label carry the meaning. Always offer Type instead, mute/stop, retry and close. A persistent mic is permitted only after consent, with an obvious stop control and cleanup on leaving. Do not animate a listening orb during a lost connection. Keep the transcript scrollable while the shop card fills; do not force the last message into view while the person reads an earlier turn.

`ReviewDialog` is the authority boundary: show proposed changes, source uncertainty, currency/units and what confirming does. Model output is a proposal. Google identity, merchant authority, face matching, liveness, publishing and execution each retain independent status. The requested soft voice is a product preference; these silent fixture videos cannot validate voice identity or speech quality.

## 4. Bottom sheet versus full-screen journey

**Published guidance.** Material describes sheets as secondary content anchored to current context. [Bottom-sheet guidance](https://m3.material.io/components/bottom-sheets/guidelines). The page did not expose detailed body content through the text fetch; precise behavior here follows the vendored component/overlay guidance and web dialog mechanics, not an invented quotation.

**Recommendation.** Full-screen for onboarding, camera/map editing and any multi-step task whose keyboard or content consumes most of a phone. A sheet fits a short contextual menu/quantity choice or review. Do not stack an editor over a sheet over a confirmation. Advance within one surface, preserve Back/draft state, name the current step and move focus to its heading. Desktop should use a bounded form with a supporting preview, rather than stretching a phone sheet to the viewport.

`Sheet.tsx:132` provides scroll containment; check that sticky actions remain outside the scrolling content, above safe areas and the IME, and never obscure focus. Choose `Dialog`, `Drawer`, `Button`, `TextField`, `List` and `Alert` by semantics. MUI theme customization supplies defaults and component overrides; it is separate from official Material design conformance. [MUI theming](https://mui.com/material-ui/customization/theming/).

## 5. Density and calm reading

**Recommendation; product trial thresholds, not a published standard.** On 390×844, use 16px starting side gutters, 8–12px related gaps and 20–24px between groups, using the existing 4px MUI spacing unit. Preserve 48px action targets. Show one decision headline, a short explanation, and one primary action in the first task viewport. Put secondary metadata in a list or expandable detail. Do not shrink labels or put every row in a card to fit more content.

Owner My shop: reveal capability through ordered sections and next-step suggestions; avoid 12 equally colourful tiles. Forecast: headline conclusion, units/method/range, chart, one action. Supplier results: composer stays reachable and cards do not capture its tap area. Customer Ask: prompt and a finite selection of useful finds, then a real stopping point. Passport: first explain where to scan, what earns a stamp, where progress is stored and what the reward means; celebration comes after eligibility.

The heatmap records visible semantic elements per 100k viewport pixels, 6×12 grid overlap counts, chromatic background hue bins, 4px spacing-rhythm share, small targets and axe contrast results. It excludes hidden/inert and center-occluded elements. Parent and child containment can still double-count; viewport clips are intentional. Hue bins count styled surfaces, not perceived accent salience. A high density/hue count triggers human review, never an automatic redesign. A calm screen can still be inaccessible; passing contrast can still feel tiring.

## 6. Typography for Indic and CJK

**Published guidance.** W3C's layout resources discuss script-specific segmentation, line breaking and baseline/line-height requirements. The Indic draft is focused mainly on Devanagari and must not be generalized as a complete Tamil/Bengali rulebook. [Indic layout requirements](https://www.w3.org/TR/ilreq/), [language enablement index](https://www.w3.org/TR/typography/), [line-breaking approaches](https://www.w3.org/International/articles/typography/linebreak.en).

**Recommendation.** Keep `fonts.ts`'s script loaders and system fallbacks. Match Japanese, Chinese and Korean glyph conventions using language-specific font selection, rather than assuming the first CJK family in a common fallback stack is correct for every locale. Let the browser shape complete grapheme clusters; never split titles by JavaScript character for typewriter motion. Avoid forced Latin tracking, fixed line boxes and uppercasing on Indic text. Handwritten Caveat is an accent for suitable short Latin text; script fallback should stay comfortably readable.

Use body text about 16px with a starting 1.5 line-height; validate actual script marks and increase leading where needed. This is a proposal, not a universal script metric. `theme.ts:132` currently tightens compact bodyLarge to 15/22; compare it at 200% and with Tamil/Hindi/Bengali before changing shared tokens. `CoachScreen.tsx:1137` has Tamil-specific leading; inspect other Indic scripts too. `TodayDeck.tsx:240` and `:388` use tight handwritten display leading and deserve localized screenshots. Preserve labelled prices with Intl formatting and tabular numerals for comparisons.

## 7. Accessibility acceptance and fatigue review

WCAG 2.2 supplies normative web requirements; use normal text contrast ≥4.5:1, large text ≥3:1, meaningful non-text contrast ≥3:1, reflow and spacing resilience, focus that remains visible, and appropriate target sizing. Its 24px minimum target criterion has spacing/exceptions; the product's 48px touch target is a deliberately stronger target. [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

Review light and dark equally. Dark mode should use tonal surfaces with restrained accents; light mode needs distinct containers without washed-out text. Do not use a reassuring green chip as the only success signal. Keyboard tests include opening/closing each sheet, focus restoration, visible focus, and text alternatives for scratch/swipe/drag. Test 320px reflow, 200% text, text-spacing override, long names and mixed-script labels. Browser emulation cannot establish screen-reader quality, physical reach, glare, IME behavior or comfortable long sessions.
